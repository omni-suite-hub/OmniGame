# 1. 设计标尺

每个方案必须同时满足三条，缺一即淘汰：

| 标准 | 含义 | 淘汰示例 |
| :--- | :--- | :--- |
| **只有浏览器能做** | 换成 App / 单机游戏就失去意义 | 又一个贪吃蛇 |
| **是真游戏** | 有失败条件、技巧成长、实时决策 | 读页面算分、养宠物 |
| **不与现有 144 款重叠** | 避开 arcade/puzzle/match/board/physics | 换皮的俄罗斯方块 |

**最关键的判定标准是「玩法内核」而非「主题包装」。** 一个把贪吃蛇包装成"吃网页元素"的项目，第一条就不满足——因为它去掉网页照样能玩。

## 1.1 现有 144 款的覆盖情况

实测 `catalog.js` 的品类分布：

| 品类 | 数量 | 代表 |
| :--- | ---: | :--- |
| arcade | 37 | 打砖块、像素鸟、太空小蜜蜂 |
| puzzle | 36 | 数独、连连看、汉诺塔 |
| multiplayer | 26 | 五子棋巅峰赛、双人扫雷死斗 |
| physics | 17 | 黄金矿工、登山赛车、割绳子 |
| match | 14 | 开心消消乐、羊了个羊、宝石迷阵 |
| board | 14 | 象棋、围棋、麻将接龙 |

**共同点：全部是「鼠标/键盘 + 单画布」操作。** 没有任何一款用到标签页、滚动、焦点、窗口尺寸、后退历史这些浏览器原生维度。

**总代码量 3026k 行，单游戏代码中位数 2 万字符**（最小 7.6k，最大 45.9k）。这是下面所有工作量估算的基准。

# 2. 两个创新维度

这 16 个方案分布在两个**互相独立**的维度上：

```
        互动方式（玩家做什么）
              ↑
              │
   浏览器行为型 │  场地型
   (用浏览器的  │  (用页面的
    行为当机制)  │   内容当关卡)
              │
              └──────────────→ 素材来源（内容从哪来）
```

**两条线应该并行推进。** 只做场地型，产品会变得"更好玩"；只做行为型，产品会变得"更独特"。两者结合才能形成真正的差异化。

**特别注意：** 两者共同的关键是**不读页面文本**（见第 3 节），这让隐私成本降到最低。

# 5. 《元素》：DOM 即关卡

## 5.1 一句话概念

把你正在浏览的网页结构，直接变成一张可玩的平台跳跃关卡。

## 5.2 核心机制

页面的真实 DOM 元素被映射为游戏世界：

| 页面元素 | 游戏对象 | 行为 |
| :--- | :--- | :--- |
| `<h1>` ~ `<h6>` | **平台** | 层级越深平台越矮，h1 最高 |
| `<img>` | **方块** | 可击碎 / 可收集 |
| `<table>` | **固定障碍** | 不可破坏 |
| `<pre>` `<code>` | **稀有资源** | 高分收集物 |
| `<a>` | **传送门** | 点击跳转到新页面 = 下一关 |
| `<form>` | **机关** | 触碰触发（仅计形态，不读内容） |
| 元素间空白 | **深渊** | 掉落即失败 |

## 5.3 核心玩法循环

1. 玩家在任意网页点击悬浮球 → 启动《元素》
2. 扩展扫描当前页 DOM，生成关卡几何数据
3. 页面滚动 = 摄像机纵向移动（你看到的网页位置就是镜头位置）
4. 角色在关卡中跳跃前进
5. 收集元素得分，遇到传送门进入新页面 = 下一关
6. 死亡或通关后返回

## 5.4 关键设计

**关卡是页面的 1:1 映射。** 不生成、不美化、不重排——页面长什么样，关卡就是什么样。这保证了：
- 每个网站天然不同，不存在关卡重复
- 玩家看到的真实页面和游戏关卡完全对应（俯视可对照）

**难度分层**（根据页面特征自动判定）：

| 难度 | 判定条件 | 元素构成 |
| :--- | :--- | :--- |
| 简单 | 标题 ≥ 3 且图片 ≥ 5 | h2/h3 平台 + 图片方块 |
| 中等 | 标题 ≥ 3，表格 ≥ 1 | 加入表格障碍 |
| 困难 | 标题层级 ≥ 4 层 | 加入传送门 + 需要精确跳跃 |
| **不可玩** | 标题 = 0 或可用元素 < 80 | **拒绝启动，提示换页** |

## 5.5 数值设计

| 项 | 值 |
| :--- | :--- |
| 关卡宽度 | 页面宽度，1:1 映射到 1440px 画布 |
| 关卡高度 | min(页面高度, 20000px) |
| 碰撞体密度上限 | 每 200px 宽度最多 12 个 |
| 角色跳跃高度 | 约 4 个正文行高 |
| 图片方块分值 | 100 |
| 代码块分值 | 250 |
| 传送门 | 0 分，+3 秒无敌 |
| 坠落判定 | Y 超过当前视口底边 +200px |
| 死亡惩罚 | 从上一检查点重开，不掉分 |

## 5.6 与现有游戏的差异

**诚实说明：玩法内核与 `平台跳跃`、`地铁跑酷` 属同族。** 独创性不在玩法，在**关卡生成**——它是"平台跳跃的网页生成器版"，不是全新的游戏类型。

它的价值在于：**给现有的平台跳跃玩法提供了无限的内容来源**。写一次玩法，144 个游戏目录之外多了无限关卡。

## 5.7 技术路径

```
content.js（已在 <all_urls> 运行，零新增权限）
  └─ DOM 采集层
       ├─ querySelectorAll('*') → 遍历
       ├─ offsetTop / offsetHeight（比 getBoundingClientRect 更快且不触发 reflow）
       ├─ 标签过滤：script/style/meta/link/head/noscript 剔除
       └─ 输出：{ tag, x, y, w, h }[] 纯几何数据
  └─ 消息通道 → 发给游戏运行时
       └─ 新增 message type: 'domLevel'
```

**渲染：** Canvas 2D 足够（实测剔除后仅 736~2403 个元素）。
**更新频率：** 页面几何仅在 scroll/resize 时变化 → 用 IntersectionObserver 增量更新，或节流至 100ms。**不需要每帧扫描。**

## 5.8 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **结构贫瘠页不可玩** | 高 | 实测：zhihu 239 元素且 0 个标题；taobao 3975 元素但 h1+h2 仅 2 个。必须做**「本页不适合游戏」检测并拒绝启动**，绝不能给用户一个空关卡 |
| **Shadow DOM 是盲区** | 中 | 实测：github 有 **373 个 shadow host**（8 站最高）。采集不到其内部结构，需在 UI 明确标注「简化关卡」 |
| 图片密集页 | 中 | 实测：CSDN 有 227 张图，会生成过密关卡。需密度上限 + 自动稀疏化 |
| 长页面卡顿 | 低 | 高度上限 20000px，超出部分不生成 |
| 用户觉得"页面被监视" | 中 | 全程不读 textContent/URL/属性值，需在权限说明里写清楚 |

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |

| 关卡生成器 | 8k | 密度控制 + 密度上限 + 不可玩检测 |

# 6. 《织网》：超链接即地图

## 6.1 一句话概念

网页上的所有超链接构成一张有向图，你在图上行走，在有限步数内完成结构性的目标。

## 6.2 核心机制

**只读取链接的 `href` 与目标页的域名 + 标题，不读任何正文。**

玩家在当前网页中点选一个链接 → 跳转 → 视角落到新页面的链接列表 → 选择下一个目标。逐步构建出一条路径。

## 6.3 关卡目标（结构型，全部不依赖内容语义）

| 目标类型 | 条件 | 难度 |
| :--- | :--- | :---: |
| 同源深潜 | 连续 5 次跳转都在同一注册域名内 | 入门 |
| 外链探险 | 走出 3 条互不重复的外部链接路径 | 入门 |
| 精准跳跃 | 在 8 步内从域名 A 到达域名 B | 进阶 |
| 深度巡航 | 访问路径深度 ≥ 4 的页面 | 进阶 |
| 回环闭合 | 找到一条回到起点的路径 | 困难 |
| 孤岛求生 | 找到只有 ≤ 2 个出链的"孤岛"页面 | 困难 |

## 6.4 核心玩法循环

1. 玩家在当前页启动《织网》
2. 扩展展示当前页的所有出链（显示域名 + 标题，不显示 URL 全串）
3. 玩家选择一个链接前往
4. 累计步数，更新目标进度
5. 达成目标 → 结算；步数耗尽 → 失败
6. 挑战成功解锁"地图"成就（记录你去过的域名拓扑）

## 6.5 数值设计

| 项 | 值 |
| :--- | :--- |
| 单关步数上限 | 8 ~ 15（按难度） |
| 评分 | `max(0, (步数上限 - 实际步数 + 3) × 100)` |
| 目标失败 | 步数耗尽仍未达成 |
| 页面出链显示 | 最多 20 个（按结构多样性排序，不按数量） |
| 成就记录 | 保存域名拓扑图，**不保存具体 URL** |

## 6.6 为什么是真游戏

有限步数内的图路径规划是真正的策略问题——不同的目标类型对应不同的最优策略，玩家需要：
- 观察当前节点的出链结构（数量、域名分布）
- 推演剩余步数下的可达性
- 权衡风险（走进死路 vs 保守推进）

有明确的成功条件、有最优解概念、有失败代价。

## 6.7 独一份性

超链接网络是网页的骨架。移动端 App 没有"页面间超链接构成的图"这个对象，桌面软件也没有。**这是浏览器独有的结构。**

## 6.8 技术路径

```
content.js
  └─ 出链采集：document.querySelectorAll('a[href]')
       ├─ 过滤：javascript: / mailto: / #锚点 剔除
       ├─ 过滤：重复 href 合并（按规范化后的 URL）
       ├─ 提取：{ href, 目标域名, 目标标题 }
       └─ ⚠️ 不读取链接文本以外的任何页面内容
  └─ 跳转：chrome.tabs.update() 或用户手动点击
       └─ 新页面的 content.js 重新采集并通过 storage 汇报
```

**跨页通信：** 新页面加载后写入 `chrome.storage.local`，原页面监听 `storage.onChanged` 推进状态。

## 6.9 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| 变成"随机点击" | 高 | 目标必须来自**结构**（域名、路径深度、层级），绝不能来自内容语义 |
| 隐私观感 | 中 | 只取域名 + 标题，不存 URL。需在 UI 明确展示"本关卡不会记录你访问的完整网址" |
| 跳转可能触发真实导航 | 中 | 建议默认"新标签页打开"而非覆盖当前页 |
| 死链 | 低 | 目标页无法加载时明确提示，不计入步数 |
| 跨域 iframe 内的链接 | 低 | 无法读取，统计中标注"不完整" |

## 6.10 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 出链采集 | 5k | 过滤 + 规范化 + 提取 |
| 目标系统 | 6k | 6 类目标 + 达成检测 |
| 跨页状态机 | 5k | storage 通信 + 步数管理 |
| UI 与反馈 | 4k | 节点展示 + 进度 + 结算 |
| **合计** | **约 20k** | **3-4 天** |

# 7. 《差分》：记忆对赌

## 7.1 一句话概念

进入动态页面，15 秒浏览记忆；页面刷新后，指出哪些内容变了。

## 7.2 核心机制

1. 玩家打开一个动态页面（新闻、榜单、电商、社交 feed）
2. 扩展已缓存上次访问时的页面结构快照
3. **15 秒倒计时**，玩家浏览并记忆
4. 倒计时结束，页面自动刷新（真实刷新）
5. 玩家在**新的页面**上指出变化了的位置
6. 结算：命中数 - 误报 × 1.5 = 得分

## 7.3 快照存什么（关键设计）

**只存结构，不存内容。**

| 存储 | 不存储 |
| :--- | :--- |
| 元素数量、位置、尺寸 | 元素文本内容 |
| 图片的占位尺寸 | 图片 URL |
| 链接的域名 | 链接完整 URL |
| 整体布局分区 | 表单内容 |

这样既保证隐私，也避免存储膨胀。

## 7.4 结构归一化（最大的技术坑）

页面的差异必须**归一化**，否则差异点过多导致不可玩：

| 归一化操作 | 说明 |
| :--- | :--- |
| 剔除动态区域 | 移除 `position: fixed/sticky` 元素、广告位、动画元素 |
| 网格对齐 | 坐标量化到 16px 网格，容忍亚像素抖动 |
| 尺寸分桶 | 尺寸量化到 8px 分桶 |
| 剔除时间戳区域 | 匹配常见时间格式文本的父容器 |
| 数量上限 | 差异点超过 25 个时判定"本页变化过大"，重新采样 |

**这是这个项目最关键的技术点。** 归一化做得不好，玩家会看到 200 个"差异"，直接放弃。

## 7.5 数值设计

| 项 | 值 |
| :--- | :--- |
| 记忆时长 | 15 秒（可调 10 / 15 / 20） |
| 差异点数量 | 5 ~ 15（按页面动态程度自动采样） |
| 命中得分 | +100 |
| 误报扣分 | -150 |
| 漏报 | 0 分（不额外惩罚） |
| 最高分 | 1500（15 个全中） |
| 对战模式 | 好友对战，同页面同种子，60 秒内比命中数 |

## 7.6 为什么是真游戏

工作记忆是**真实的认知能力**，不是运气。有明确的技巧提升空间：
- 玩家会学会优先记忆"视觉特征明显"的位置（图片、颜色块、大数字）
- 熟练玩家发展出"分区扫描"策略
- 记忆时长本身就是难度旋钮

## 7.7 独一份性

浏览器插件能安全地做"上次访问的页面快照"——因为它在同一个权限域内。普通网页做不到（会被同源策略阻止），App 也没有对应的"页面快照"概念。

## 7.8 技术路径

```
content.js
  ├─ 首次访问：采集归一化快照 → chrome.storage.local
  │     key = hash(hostname + pathname)  ⚠️ 不存完整 URL 到云端
  ├─ 二次访问：读取旧快照 → 开启 15s 倒计时
  ├─ 倒计时结束：真实 location.reload()
  └─ 刷新后：采集新快照 → diff(旧, 新) → 生成差异点列表
       └─ 玩家点击 → 判定命中/误报
```

## 7.9 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| 差异点过多不可玩 | **高** | 结构归一化 + 变化过大时重新采样 + 上限 25 |
| 存储膨胀 | 中 | 快照只存几何，压缩后单页约 2-5KB；限制最多缓存 50 页，超出用 LRU 淘汰 |
| 页面无变化 | 中 | 变化 < 3 点时提示"本页面较稳定，换个页面试试" |
| 强制刷新打扰用户 | 中 | **绝不能自动刷新**。改为"点击按钮开始第二局"，用户主动触发 |
| 隐私 | 中 | 快照只存几何，**不存任何文本** |

| :--- | ---: | :--- |

| 差异算法 | 6k | diff + 采样控制 |

# 8. 《对撞》：你的页面对手你的页

## 8.1 一句话概念

双人对战。**各自的当前页面生成战斗力**，不含任何具体内容。

## 8.2 核心机制

**隐私铁律：只上报统计数字，绝不上报 URL。** 这条一旦破，产品就完了。

| 页面特征 | 战力资源 | 上限 |
| :--- | :--- | :---: |
| 超链接数 | 远程攻击 | 300 |
| 图片数 | 护盾 | 500 |
| 文本块数 | 弹药 | 250 |
| 标题层级深度 | 射程 | 距离倍率 |
| 表单数（只数个数） | 干扰 | 200 |
| 表格数 | 护甲 | 150 |

## 8.3 为什么"用页面作战"是合理的

- 打开 30 个标签页的用户 → 弹药与护盾都强，但**干扰值也高**（自己的页面在"分心"）
- 只开一个深度阅读页的用户 → 攻击高但脆
- **不存在最优配置** —— 你必须根据自己的真实工作状态取舍

这让游戏和用户的真实行为形成张力，而不是奖励"多开标签页"。

## 8.4 核心玩法循环

1. 双方各自在战斗开始时停留在任意网页
2. 扩展统计该页特征 → 生成属性面板
3. 回合制：移动 / 攻击 / 护盾充能
4. 玩家可**消耗行动力刷新页面**（重roll属性）但有代价
5. 击败对手结算

## 8.5 数值设计

| 项 | 公式 |
| :--- | :--- |
| 攻击力 | `min(链接数 × 3, 300)` |
| 护盾 | `min(图片数 × 5, 500)` |
| 弹药 | `min(文本块数 × 2, 250)` |
| 射程 | `标题最大层级 × 60` px |
| 干扰 | `min(表单数 × 20, 200)` |
| 护甲 | `min(表格数 × 30, 150)` |
| 刷新代价 | 消耗 1 行动力 + 本回合攻击力 -30% |

**平衡目标：** 让"文档页"（高攻低血）和"电商页"（高血低攻）各有胜率，页面结构显著影响策略。

## 8.6 为什么是真游戏

有实时对抗、有资源取舍、有属性克制。页面结构 = 初始配置，玩家理解配置优势后会主动选择适合自己的页面——这个决策本身就是玩法。

## 8.7 技术路径

**复用现有的 `omni-net.js`（30KB，已含 RTCPeerConnection + iceServers + 完整信令）。** 这是 OmniGame 最大的资产优势。

```
content.js 采集统计 → storage
  └─ 只写 { links, imgs, texts, headingDepth, forms, tables }  ⚠️ 绝不写 URL
background.js
  └─ WebRTC DataChannel 传输统计数字
  └─ 本地权威：房主计算回合结果
```

**⚠️ 关键设计：信令必须走 P2P，不能有第三方服务器。** 一旦引入信令服务器，就违背了 OmniGame"零外部请求"的立身之本。需要用手动交换 SDP（复制粘贴）或局域网发现——这需要在开发阶段就确定方案。

## 8.8 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| 隐私质疑 | **极高** | 代码层面确保不上报 URL；UI 明示"只发送 6 个数字"；隐私政策单独说明 |
| 联机信令无服务器 | **高** | 必须解决。方案：手动复制 SDP / 同局域网发现 / 或接受"需手动邀请"的低频体验 |
| 页面类型单一导致 build 单一 | 中 | 统计面板明确展示，让玩家理解"换页可以换流派" |
| 弱网 | 中 | 断线时降级为本地 AI 对手 |

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 统计采集 | 4k | 6 项特征（不含 URL） |
| 属性计算与平衡 | 4k | 公式 + 克制关系 |
| 回合制逻辑 | 8k | 状态机 + 战斗结算 |
| 联机层 | 10k | 复用 omni-net.js + 无服务器信令 |
| UI | 7k | 属性面板 + 战场 |
| **合计** | **约 33k** | **5-6 天** |

# 9. 《折叠》：窗口宽度即资源

## 9.1 一句话概念

你必须拖动浏览器窗口的边缘改变宽度，才能让角色通过通道。

## 9.2 核心机制

游戏场景是一个横向通道。**通道的安全宽度由你的浏览器窗口宽度决定**——窗口太宽，两侧墙壁挤进来；窗口太窄，角色会掉出去。

```
┌─────────────────────────────┐
│      浏览器窗口边缘          │
│  ┌───────────────────────┐  │
│  │   ← 安全通道 →         │  │
│  │      ▓▓▓▓▓            │  │  ← 墙壁随窗口宽度内移
│  │   ▓        ▓          │  │
│  │   ▓   ▲    ▓          │  │  ▲ = 角色
│  │   ▓        ▓          │  │
│  └───────────────────────┘  │
└─────────────────────────────┘
```

## 9.3 核心玩法循环

1. 玩家启动游戏，场景出现一条宽度不定的通道
2. 玩家**拖动浏览器窗口边缘**，让窗口宽度落在绿色容差带内
3. 容差带内，角色自动前进
4. 通过后进入下一关，通道更窄
5. 误操作导致角色碰撞 → 失败

## 9.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 窗口宽度映射 | 200px → 1600px 映射到游戏坐标 |
| 容差 | ±3%（约 ±24px @ 800px 窗口） |
| 关卡推进 | 每关通道收窄 40px |
| 关卡数 | 12 关（从 1200px 收到 240px 容差） |
| 限时 | 15 秒 / 关 |
| 失败判定 | 角色碰到墙壁 |

**难度曲线：** 容差带从 120px 逐步收窄到 40px，最后三关容差小于窗口拖动的最小像素步进（通常 10px），形成真实挑战。

## 9.5 独一份性

窗口尺寸是浏览器的真实状态，**App 里完全没有这个东西**。玩家操作的不是游戏内的虚拟滑块，而是操作系统层面的窗口边框。

## 9.6 技术路径

```
content.js
  └─ window.resize 事件 → 读取 window.innerWidth
  └─ 节流（16ms）→ 更新游戏状态
  └─ 每帧渲染：角色位置由「当前窗口宽度 - 容差中心」计算
```

**关键设计：游戏画布宽度 = window.innerWidth 实时绑定。** 窗口一变，整个关卡视觉立刻变化，手感极强。

## 9.7 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **窗口拖拽手感差** | 高 | 必须提供键盘辅助：← → 键微调窗口宽度（通过 `window.resizeTo` 在允许时生效）或直接调整游戏内"虚拟宽度" |
| 最小窗口限制 | 中 | 多数浏览器最小宽度 300-500px，关卡设计要适配 |
| macOS 全屏下无法拖拽 | 中 | 全屏时降级为"键盘调节"模式 |
| 误触发（用户想调整窗口看别的） | 中 | 游戏期间在画布上明确提示"窗口宽度是游戏的一部分" |
| 窗口管理器差异 | 低 | 各系统行为不同，需实测 |

## 9.8 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 宽度绑定与渲染 | 5k | resize 监听 + 实时渲染 |
| 关卡与角色物理 | 6k | 通道生成 + 碰撞 |
| 键盘辅助方案 | 3k | 无障碍 + 降级 |
| UI 提示 | 1k | 引导 |
| **合计** | **约 15k** | **2-3 天** |

# 10. 《纯滚》：滚动是唯一输入

## 10.1 一句话概念

全程只能用鼠标滚轮。不能点击。页面纵向长度就是竖井深度。

## 10.2 核心机制

- 角色在竖井中垂直移动
- **只能通过滚轮改变位置**，无其他输入
- 精确控制每次滚动的距离，以通过精确的间隙
- 快速滚动 = 冲刺（但增加过热）
- 停留 = 扫描隐藏矿点

## 10.3 核心玩法循环

1. 玩家启动游戏，竖井生成
2. 滚轮向下 = 下潜，向上 = 上浮
3. 通过间隙收集矿石
4. 避开过热区与塌方点
5. 到达底部宝藏层

## 10.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 竖井深度 | 5000px（10 屏） |
| 最小滚动步进 | **需实测确定**（鼠标滚轮通常 100px/格，触控板连续） |
| 精确度要求 | 关键间隙宽度 = 1.5 倍滚动步进 |
| 过热 | 每 100ms 滚动 +1，快速滚动 +3，静止 -2/s |
| 过热上限 | 100 → 强制上浮 + 3s 锁定 |
| 矿石 | 4 种（普通/银/金/晶体） |
| 陷阱 | 3 种（过热区/塌方/虚假矿石） |

## 10.5 独一份性与设计意图

滚轮是浏览器的原生输入设备。**精确控制滚动距离本身需要技巧**——因为浏览器有滚动惯性，你必须学会"点按"而非"滑动"来获得精确的小幅位移。

这让一个最普通的浏览器动作变成了技巧性操作。

## 10.6 风险（这是全表最高风险的项目）

| 风险 | 严重度 | 说明 |
| :--- | :--- | :--- |
| **跨设备手感差异极大** | **极高** | 鼠标滚轮是离散跳跃（通常 100px/格），触控板是连续惯性，触屏是触摸模拟滚动，键盘 PageUp/Down 是整屏跳转。**这四种输入无法用一套参数统一** |
| 惯性差异 | 极高 | macOS 弹性滚动、Firefox 的 `scroll-behavior: smooth`、Windows 的分段滚动 —— 停止距离都不同 |
| 用户习惯冲突 | 中 | 大多数用户滚动是"快速翻页"的肌肉记忆，突然要求精确微调会很不适应 |

**必须做的适配工作：**
1. **设备探测**：识别滚轮类型（`WheelEvent.deltaMode`：`0`=像素 / `1`=行 / `2`=页）
2. **每设备独立参数**：为鼠标/触控板/触屏/键盘各做一套手感调校
3. **校准引导**：开局让玩家滚动几次，自动学习其步进值
4. **可访问性**：必须提供键盘替代方案

**我的判断：这个项目的风险主要在手感调校而非代码。** 如果第一周手感调不好，整个项目应该中止。

## 10.7 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 滚动采集与归一化 | 4k | deltaMode 处理 + 步进学习 |
| 角色与关卡 | 6k | 物理 + 间隙生成 |
| 多设备适配 | 4k | 4 套参数 + 校准 |
| 陷阱与矿点 | 3k | 3 种陷阱 + 4 种矿 |
| **合计** | **约 17k** | **3-5 天（含手感调校）** |

# 11. 《回声》：视觉延迟，靠耳朵玩

## 11.1 一句话概念

主要反馈通道是声音。目标会发出音效，但视觉出现延迟 800ms —— 你必须靠听觉判断。

## 11.2 核心机制

```
真实时间轴：
  t=0ms     声音出现        视觉还没出现
  t=800ms   视觉出现        ⚠️ 你看到的已经是 800ms 前的世界
```

玩家需要：
1. 听声音判断目标方位（左右、高低、远近）
2. 在视觉出现前提前操作
3. 声音与视觉的错位形成持续干扰

## 11.3 核心玩法循环

1. 目标在随机位置生成并播放音效
2. 玩家根据声音判断位置
3. 在视觉出现前（800ms 窗口）做出反应
4. 视觉出现后可以校正，但已经晚了
5. 连续命中提升难度

## 11.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 视觉延迟 | 800ms（难度递增：600 / 800 / 1100） |
| 反应窗口 | 1.2s |
| 命中判定 | ±150ms |
| 目标种类 | 6 种音高 × 4 种方位 = 24 种 |
| 难度递增 | 每 5 次命中延迟 +100ms，上限 1100ms |
| 目标体积 | 视觉出现后需点击，缩小窗口 700ms |

## 11.5 双人变体（最硬核）

| 角色 | 能看 | 能听 | 能操作 |
| :--- | :--: | :--: | :--: |
| A（观察者） | ✓ | ✗ | ✗ |
| B（操作者） | ✗ | ✓ | ✓ |

两人被迫分工协作。这是把信息不对称做到极致的设计。

## 11.6 独一份性

用 Web Audio API 做**精确的视听延迟错位**，需要音频引擎和渲染循环的精确配合。这种"故意制造感知不一致"的玩法在传统游戏中很少见（多用于心理实验）。

## 11.7 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **公共场合无法发声** | **高** | 必须提供**完整视觉降级方案**：把"延迟视觉"改为"延迟色块"或"延迟轮廓"，保证无声环境下可玩 |
| 听力差异 | 中 | 音量可调 + 音高区分度大 + 提供视觉提示选项 |
| 耳机依赖 | 中 | 明确提示"建议佩戴耳机" |
| 音频延迟 | 中 | `AudioContext` 有输出延迟，需 `getOutputTimestamp()` 校准 |

**关键点：视觉降级方案不是可选项，是必须项。** 地铁上打开这个游戏的人很多，如果只能靠听，产品的可用性会很差。

| :--- | ---: | :--- |
| 音频引擎 | 5k | Web Audio + 精确调度 |
| 目标与判定 | 5k | 生成 + 窗口判定 |
| 视觉降级方案 | 4k | 无声模式 |
| 双人模式 | 8k | 角色分工 + 同步 |

# 12. 《沉睡》：把后台节流做成叙事

## 12.1 一句话概念

Chrome 会把后台标签页的定时器节流到约 1 分钟一次。你的世界在你切走后**几乎停滞** —— 某些关卡必须利用这一点才能通关。

## 12.2 核心机制

```
前台：setInterval(16ms) → 世界正常速度
后台：被节流到 ~60s 一次 → 世界几乎停滞
```

某些关卡的解法是**必须离开页面**，利用节流让世界"跳过"一段时间。

## 12.3 关卡设计

| 关卡类型 | 解法 |
| :--- | :--- |
| 停滞关 | 需要等待某个倒计时结束，但前台等待太慢 → 必须切走 |
| 跳跃关 | 平台只在"世界停滞"时出现（因为需要玩家离开才会消失的逻辑漏洞） |
| 收尾关 | 敌人只在后台移动 → 必须切走才能甩掉它 |

## 12.4 核心玩法循环

1. 玩家启动关卡
2. 某些机制需要时间累积
3. 玩家切到其他标签页
4. 回来后发现世界只走了几秒（或按节流周期跳了一段）
5. 利用这个时间差过关

## 12.5 数值设计

| 项 | 值 |
| :--- | :--- |
| 前台 tick | 16ms（60fps） |
| 后台 tick | 约 60s（由浏览器决定，不可控） |
| 停滞关需要等待 | 120 秒（前台）→ 后台 2 个周期即可 |
| 敌人移动（仅后台） | 每次 tick 移动 1 格 |
| 提示 | 明确告知"切换标签页是解法的一部分" |

## 12.6 独一份性

**把浏览器的技术缺陷（后台节流）变成了可玩机制**，而不是对抗它。这是我认为这个方案最巧妙的地方。

## 12.7 风险（必须正视）

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **节流行为跨浏览器差异极大** | **高** | Chrome 后台标签页 ~1min；Firefox 行为不同；Edge 同 Chrome；Brave 同 Chrome。**必须做运行时探测，不能假设节流一定发生** |
| 用户不理解机制 | 高 | 需要极清晰的前置教学："这个关卡需要你离开页面" |
| 用户以为游戏卡了 | 中 | 切走前明确提示"世界将放慢，这是设计" |
| 检测失败 | 中 | 若探测到未节流，改为"手动推进"替代方案 |

**技术要求：**
- 关卡开始前必须跑一次节流探测（前台启动定时器 → 切后台 → 检测实际 tick 间隔）
- 探测失败则整个关卡不可用 → 需要有降级设计

## 12.8 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 节流探测 | 4k | 跨浏览器检测 + 降级 |
| 世界时间管理 | 4k | 前台/后台双时间源 |
| 关卡设计 | 4k | 3 类关卡 |
| 教学与提示 | 2k | 引导 |
| **合计** | **约 14k** | **2 天** |

# 13. 《倒带》：后退键是通关道具

## 13.1 一句话概念

关卡设计成「必须先破坏，再后退穿越」。浏览器后退键从失误变成时间旅行。

## 13.2 核心机制

**具体例子：**

```
初始状态：角色在桥左岸，桥完好，开关关闭
  ↓ 走过桥
状态 B：角色在桥上，开关关闭
  ↓ 拉下开关（机关启动，桥开始崩塌）
状态 C：角色在桥上，桥崩塌中，开关已开
  ↓ 按浏览器后退
状态 D：⚠️ 角色在桥上，开关已开，桥完好
```

**状态 D 是正常流程无法到达的** —— 只有后退穿越能产生它。这就是全部玩法。

## 13.3 元素与规则

| 元素 | 行为 |
| :--- | :--- |
| 门 | 开关控制，切换时所有门状态反转 |
| 桥 | 可被机关摧毁 |
| 箱子 | 可推动，改变机关触发条件 |
| 尖刺 | 触碰即失败 |
| 目标点 | 到达即通关 |

**核心规则：后退一次 = 回到上一个快照，但快照中「已经被改变的部分保持改变」。**

## 13.4 关卡设计

12 关，每关一个"必须后退才能到达的状态"：

| 关 | 谜题 | 需要的回退次数 |
| :--: | :--- | :--: |
| 1 | 教学：单开关 | 1 |
| 2 | 双开关互斥 | 2 |
| 3 | 箱子改变通路 | 2 |
| 4 | 桥的时序 | 1 |
| 5-8 | 组合谜题 | 2-3 |
| 9-12 | 多层状态机 | 3-5 |

## 13.5 数值设计

| 项 | 值 |
| :--- | :--- |
| 后退次数限制 | 3 ~ 5（按关卡） |
| 失败 | 尖刺触碰 / 后退次数耗尽 |
| 快照粒度 | 每次状态变更时快照 |
| 提示 | 通关后展示"你用了 N 次后退" |

## 13.6 独一份性

**★★★★★。这是 16 个方案里独一份度最高的。**

浏览器历史是一个免费的、可重复穿越的存档系统。移动端的返回键语义是"退出应用"，完全无法实现这个玩法。桌面软件也没有跨状态的"时间倒流"。

用户对后退键的直觉是"退回去"——把它变成"前进到另一个平行状态"，认知冲击极强。

## 13.7 风险（第二个高风险项目）

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **接管后退会干扰真实导航** | **极高** | 必须在游戏开始时**明确拦截并提示**："本关卡中后退键是玩法的一部分"。提供独立的退出键（Esc）。游戏结束后恢复导航 |
| 用户本能反应 | 高 | 大量用户会下意识后退退出游戏 → 需要强引导 + 二次确认 |
| 浏览器历史 API 限制 | 中 | `pushState` 只能同文档；需要用 `history.replaceState` 伪造快照 |
| 关卡设计难度 | 中 | 12 关手工设计，"必须后退才能到达"的状态构造很费脑子 |
| 刷新行为 | 低 | 刷新 = 丢失进度（可接受） |

**技术要点：**
```
每个状态变更 → history.pushState({ level: N, snapshot })
后退 → popstate 事件 → 恢复快照 BUT 保留"门/桥"的当前状态
关卡结束 → 连续 history.back() 清理 + 恢复导航
```

## 13.8 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 快照系统 | 6k | pushState + popstate + 状态合并 |
| 元素与物理 | 6k | 门/桥/箱/尖刺 |
| 关卡数据 | 4k | 12 关手工设计 |
| 导航拦截与恢复 | 3k | 强提示 + 退出机制 |
| **合计** | **约 19k** | **3-4 天** |

# 14. 《缓冲》：标签页数量决定世界速度

## 14.1 一句话概念

你的游戏世界速度 = 浏览器实时负载。开 20 个标签页，世界几乎停滞。

## 14.2 核心机制

```
速度 = f(当前打开的 OmniGame 相关标签页数)

标签页 < 5   → 正常速（1.0×）
5 ~ 15       → 变慢（线性衰减）
> 15         → 几乎停滞（0.15× 地板）
```

玩家角色必须持续向前跑，速度不足会撞上后面的墙壁。

## 14.3 核心玩法循环

1. 玩家启动游戏，角色开始自动奔跑
2. 玩家同时在多个标签页中打开游戏
3. 标签页越多，所有标签页里的世界越慢
4. 玩家必须在"保留工作标签页"和"维持游戏速度"之间选择
5. 达到 1000 米即通关

## 14.4 为什么这个设计是诚实的

**它把"标签页太多导致卡顿"这个真实痛点直接变成核心机制。** 不是套个皮说"你开标签页我给你加分"，而是：开太多标签页，游戏真的会更慢。

玩家会真切体验到"整理标签页原来这么有价值"—— 但这次是通过游戏，而不是说教。

## 14.5 数值设计

| 项 | 值 |
| :--- | :--- |
| 目标距离 | 1000m |
| 速度公式 | `60 × clamp(1 - (tabs - 3) / 20, 0.15, 1)` |
| 角色位置更新 | 每帧基于当前速度积分 |
| 撞墙判定 | 位置后退到 0 |
| 统计频率 | 100ms |
| 计分 | 到达距离 + 剩余速度奖励 |

**平衡验证：** 5 个标签页 → 1.0× → 舒适。10 个 → 0.55× → 紧张。20 个 → 0.15× → 几乎无法前进。玩家会主动关掉标签页。

## 14.6 技术路径

**关键：必须做到零新增权限。**

```
每个标签页的 content.js
  └─ 每 500ms 写一次心跳：chrome.storage.local.set({ 'omg:beat': { t, id } })
  └─ 用 BroadcastChannel 更优（不写 storage，无痕）
同一标签页的多个游戏实例
  └─ BroadcastChannel('omg-tabs')
  └─ 统计 2 秒窗口内的活跃心跳数 = 标签页数
```

**为什么用 BroadcastChannel 而不是 storage：**
- `storage.onChanged` 会跨标签页触发，写入过于频繁有开销
- BroadcastChannel 是同源广播，专为跨标签页通信设计
- 两者都不需要 `tabs` 权限

## 14.7 风险

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| 后台标签页节流影响心跳 | 中 | 后台定时器被节流 → 心跳变稀疏 → 会误判为"标签页关闭"。**解决：节流感知**（心跳时间戳间隔超过 1s 则视为后台但仍存活） |
| 用户觉得被监视 | 中 | UI 明确显示"当前检测到 N 个游戏标签页"并允许"只统计本窗口" |
| 多窗口 | 中 | 同源标签页会互相广播，需明确是否跨窗口统计 |
| 玩法单一 | 中 | 中期需加入"加速道具"等变化 |

## 14.8 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 心跳与统计 | 4k | BroadcastChannel + 节流感知 |
| 速度与物理 | 5k | 公式 + 积分 |
| UI 与反馈 | 3k | 标签页计数显示 |
| 稳定性 | 3k | 多窗口 + 异常处理 |
| **合计** | **约 15k** | **2-3 天** |

# 15. 《断章》：一次性的游戏

## 15.1 一句话概念

状态只在内存。**关掉页面、刷新、切走 —— 永久丢失，不能存档。**

## 15.2 核心机制

1. 玩家开始一局，所有进度在内存中
2. 关掉标签页 / 刷新 / 切走超过一定时间 → 进度归零
3. 只能记录"历史最长记录"，不记录任何进度
4. 每次都是全新的、不可逆的一局

## 15.3 核心玩法循环

1. 玩家启动，进入随机生成的关卡
2. 一路向前，能走多远走多远
3. 随时可能因为关掉页面而结束
4. 结束后只显示"你走到了第 X 米 / 历史最佳第 Y 米"
5. 玩家为了刷新记录会反复尝试

## 15.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 关卡 | 程序生成，每次不同 |
| 存活判定 | `visibilitychange` 隐藏超过 3 秒即判定结束 |
| 存储内容 | **仅** `{ bestDistance, playCount }` |
| 不存储 | 关卡种子、当前位置、任何进度 |
| 提示 | 开局明确"这一局没有存档" |

## 15.5 为什么"不能存档"反而是设计

浏览器里"随手关掉一个标签页"这个动作的分量，在其他媒介里不存在。App 切换任务会被记住，桌面软件关闭窗口意味着退出。

**这把"用户的随意行为"变成了游戏的一部分。** 你必须珍惜这一局。

## 15.6 风险与规避

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **用户当成 bug** | **高** | 必须在开局前用全屏提示明确说明，并提供"先看看规则"按钮。结束页要说"这是设计" |
| 误触丢失 | 中 | 切走 3 秒内回来不算（给缓冲） |
| 挫败感 | 中 | 失败页强调"历史最佳"和"再试一次"的低成本 |
| 存储作弊 | 低 | 记录数据不敏感，作弊成本也低 |

## 15.7 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 关卡生成 | 5k | 程序化 |
| 生命周期管理 | 4k | 可见性检测 + 缓冲 |
| UI 与引导 | 5k | 规则说明（关键） |
| 记录 | 2k | 最好成绩 |
| **合计** | **约 16k** | **2-3 天** |

# 16. 《和弦》：物理修饰键状态

## 16.1 一句话概念

需要按真实修饰键组合（`Ctrl` / `Alt` / `Meta` / `Shift`）来演奏，像弹和弦一样。

## 16.2 核心机制

用 `KeyboardEvent` 的 `ctrlKey` / `altKey` / `metaKey` / `shiftKey` 状态组合判断，而不是字符。

**6 类和弦：**

| 和弦 | 组合 | 分数 |
| :--- | :--- | ---: |
| 单音 | `↑` | 10 |
| 和音 | `Ctrl + ↑` | 25 |
| 属音 | `Alt + ←` | 25 |
| 减音 | `Shift + →` | 25 |
| 属七 | `Ctrl + Alt + ↑` | 50 |
| 导七 | `Meta + Shift + ←` | 50 |

## 16.3 核心玩法循环

1. 屏幕上依次落下音符（提示按键组合）
2. 玩家在正确时机按下正确的组合
3. 命中判定 ±120ms
4. 连击提升倍率
5. 漏按或错按断连击

## 16.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 判定窗口 | ±120ms |
| 下落速度 | 3 档，随难度递增 |
| 连击倍率 | 1× / 1.5× / 2× / 3×（每 10 连击提升） |
| 音符类型 | 6 类（对应上表） |
| 谱面 | 程序生成 + 固定种子挑战 |

## 16.5 独一份性

`KeyboardEvent` 能读到**物理修饰键的独立状态**。这和"按住 Shift 打大写字母"是不同的信息层。游戏能要求玩家同时按下多个修饰键 —— 这是键盘输入的独有维度。

## 16.6 跨平台问题

| 平台 | 主修饰键 | 差异 |
| :--- | :--- | :--- |
| macOS | `Cmd`（metaKey） | Ctrl 与 Cmd 语义不同，Cmd+Tab 是系统快捷键 |
| Windows/Linux | `Ctrl`（ctrlKey） | Alt 会被浏览器菜单占用 |
| 全平台 | `Shift` + 方向键 | 部分系统会与文本选择冲突 |

**必须做按键映射抽象层**，让玩家在设置里选择"主修饰键"。

## 16.7 这是最值得先做的项目

**理由：1 天成本，能验证整个方向。**

它的技术假设最简单（纯键盘事件），但如果《和弦》的手感和可玩性成立，就证明了两件事：
1. 玩家愿意接受"用浏览器原生状态做输入"
2. 原创玩法在 OmniGame 的用户里跑得通

如果《和弦》不成立，损失也就一天。

## 16.8 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 按键状态机 | 3k | 组合识别 + 映射抽象 |
| 判定与谱面 | 3k | 判定 + 生成 |
| UI 与反馈 | 2k | 下落显示 + 判定反馈 |
| **合计** | **约 8k** | **1 天** |

# 17. 《对折》：双视窗延迟对战

## 17.1 一句话概念

一个屏幕上下分割，两个视窗是**延迟镜像**的棋盘。你看到对方棋盘有 300ms 延迟。

## 17.2 核心机制

**信息不对称博弈：**

- 双方在同一棋盘上下子
- 你看到的是对方 **300ms 前**的状态
- 延迟随关卡递增：300 → 600 → 1200ms
- 延迟期间用半透明"幽灵子"表示

```
你的视窗  ─ 立即显示你的落子
对方视窗  ─ 显示你的落子，但延迟 300ms
```

## 17.3 核心玩法循环

1. 双方在同一页面上下分屏
2. 轮流落子
3. 你看到的对方棋盘有延迟，必须预判
4. 先连成五子者胜
5. 延迟递增，博弈难度上升

## 17.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 棋盘 | 15×15 |
| 延迟档位 | 300 / 600 / 1200ms |
| 幽灵子透明度 | 0.35 |
| 胜利条件 | 五子连线 |
| 匹配 | 随机匹配 / 房间号邀请 |

## 17.5 为什么是双人

因为纯 AI 无法制造"不确定性"。延迟博弈的乐趣来自于**"他刚才到底下在哪"**的不确定 —— 这只有真人对战才有。

同时提供本地双人（同机分屏）作为备选，不需要网络。

## 17.6 技术路径

**最大成本不是玩法，是 `surface.js` 改造。**

现状：`surface.js` 52KB，是单视窗架构。
需要：
- 分屏渲染（两个 canvas）
- 消息同步（BroadcastChannel，同机零延迟 / WebRTC 跨机）
- 延迟缓冲队列

**阶段建议：先做同机本地双人（BroadcastChannel，零网络问题），跨机联机放二期。**

## 17.7 风险

| 风险 | 严重度 | 规避方案 |
| :--- | :--- | :--- |
| **surface.js 架构改造** | **高** | 52KB 单视窗代码，改双视窗工作量大。**建议不做双视窗，改为"双页面各自开一个游戏窗口"** |
| 联机匹配 | 中 | 优先做本地双人 |
| 延迟同步抖动 | 中 | 固定延迟而非真实网络延迟，保证公平 |

## 17.8 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 博弈逻辑 | 8k | 棋盘 + 胜负 + 延迟队列 |
| 分屏渲染 | 6k | 双 canvas |
| 同步层 | 6k | BroadcastChannel / WebRTC |
| UI | 4k | 棋盘 + 状态 |
| **合计** | **约 24k + surface 改造** | **5-6 天** |

# 18. 《窄门》：滚动速率弹弓

## 18.1 一句话概念

蓄力靠滚动，松手靠停滚。滚动速度决定弹弓力度。

## 18.2 核心机制

- 向下滚动 = 拉弓（力度随滚动速度累积）
- 停止滚动 = 松手发射
- 滚动越快，弹道越猛，但精度越差
- 需要"快速滚动后立刻停住"的技巧

## 18.3 数值设计

| 项 | 值 |
| :--- | :--- |
| 蓄力时间 | 0 ~ 1.5s |
| 力度 | 与蓄力时长成正比 |
| 精度衰减 | 力度 > 70% 时散布角 ±15° |
| 目标 | 距离 200-500px 的靶心 |
| 关卡 | 12 关，逐渐增加风力与距离 |

## 18.4 差异化不足的诚实评估

**这个方案我不推荐优先做。** 现有的 `slope`（几何冲刺）、`隧道冲刺`、`极速赛车` 已经是弹道/速度类物理游戏，玩法内核重叠度高。

它的独一份点（滚动代替点击蓄力）不足以支撑一个独立项目。**如果要做，建议作为现有某个物理游戏的一个模式，而不是新游戏。**

## 18.5 工作量

| 部分 | 字符 | 说明 |
| :--- | ---: | :--- |
| 弹道物理 | 5k | 蓄力 + 散布 |
| 关卡 | 3k | 12 关数据 |
| UI | 2k | 力度条 |
| **合计** | **约 10k** | **1-2 天** |

# 19. 《像素考古》：页面滚动即挖掘

## 19.1 一句话概念

把网页纵向长度当成矿井深度，向下滚动 = 向下挖掘。

## 19.2 核心机制

| 页面元素 | 矿脉元素 |
| :--- | :--- |
| 标题 | 矿层入口 |
| 正文段落 | 普通岩层 |
| 图片 | 矿石节点 |
| 代码块 | 稀有晶体 |
| 表格 | 结构矿脉 |
| 页面底部 | 深层宝藏 |

玩家向下滚动挖掘，采集矿石，避开过热区与塌方。

## 19.3 核心玩法循环

1. 选择当前页面作为矿井
2. 观察矿脉提示（页面元素分布）
3. 控制滚动速度与方向
4. 在节点出现时采集
5. 避开过热、塌方、虚假矿石
6. 到达页面底部取得宝藏

## 19.4 数值设计

| 项 | 值 |
| :--- | :--- |
| 矿井深度 | = 页面高度（不同网站差异巨大：1x ~ 12x 屏） |
| 矿石种类 | 4 种（正文/图片/代码/表格） |
| 陷阱 | 3 种（过热区/塌方/假矿石） |
| 装备升级 | 5 级 |
| 成就 | 10 个 |

## 19.5 差异化不足的诚实评估

**和《元素》高度重叠** —— 两者都是"页面元素 → 物理对象"。区别只是《元素》是横向平台跳跃，这个是纵向挖掘。

技术共享度高（同一个 DOM 采集层），但作为两个独立产品会显得重复。

**建议：作为《元素》的一个模式（纵向关卡），而不是独立游戏。**

## 19.6 工作量

若作为《元素》的模式：约 **4k**（复用采集层 + 纵向物理）
若作为独立游戏：约 **18k**

# 20. 共用技术基建

以下基建在多个方案间共享，**先建一次**能显著降低后续项目成本。

## 20.1 DOM 采集层（服务《元素》《差分》《对撞》）

基于实测数据的决策：

| 决策 | 选择 | 依据 |
| :--- | :--- | :--- |
| 几何 API | `offsetTop` / `offsetHeight` | 实测比 `getBoundingClientRect` 略快，且不触发 reflow |
| 遍历范围 | `querySelectorAll('*')` + 标签过滤 | 实测 4000 元素仅 0.2ms |
| 剔除规则 | script/style/meta/link/head/noscript | 零信息量 |
| 更新频率 | **不每帧扫描**，用 IntersectionObserver 增量更新或节流 100ms | 页面几何仅在 scroll/resize 时变化 |
| 存储字段 | `{ tag, x, y, w, h }` | **不含 textContent / href / src** |

**实测性能基线**（8 站点，最坏情况 wikipedia 4254 元素）：

| 方案 | 每帧耗时 | 判定 |
| :--- | ---: | :--- |
| 全树 getBoundingClientRect | 2.33ms | ✅ 60fps 预算内 |
| 全树 offsetTop/Height | 2.38ms | ✅ |
| 视口扫描 | 2.55ms | ✅ |
| 标签过滤 + 视口剔除 | 2.38ms | ✅ 保留 736~2403 元素 |

**结论：性能不是任何方案的风险点。** Canvas 2D 足够，无需 WebGL。

## 20.2 跨标签页通信（服务《缓冲》）

- `BroadcastChannel` 优于 `storage.onChanged`（不写存储、无痕）
- 两者都**不需要 `tabs` 权限**
- 必须做**节流感知**（后台标签页定时器被节流，心跳会变稀疏）

## 20.3 联机层（服务《对撞》《对折》）

复用现有 `games/_shared/omni-net.js`（30KB，已含 RTCPeerConnection + iceServers + 信令）。

**⚠️ 未解决的问题：信令必须无服务器。** 一旦引入第三方信令服务器，就违背 OmniGame"零外部请求"的立身之本。可选方案：

1. 手动复制粘贴 SDP（体验差但零依赖）
2. 局域网广播发现（同 Wi-Fi，零依赖）
3. 接受"需要手动邀请"（把联机做成小众功能）

**这个决策必须在开发前定，不能拖到实现阶段。**

## 20.4 入口复用

现有 `content.js` 已有的能力可直接复用：

| 现有 | 用途 |
| :--- | :--- |
| 悬浮球 | 天然的游戏启动入口 |
| `btnFloatWin` / `btnSidePanel` | 两种游戏形态 |
| `fetchSoloGames` | 游戏目录拉取 |
| 9 种 message type | 新增 `domLevel` / `tabCount` 等即可 |

## 20.5 需要新增的 manifest 权限

**大部分方案零新增权限。** 唯一例外：

| 方案 | 新增权限 | 商店影响 |
| :--- | :--- | :--- |
| 《沉睡》《断章》 | 无（visibilitychange 即可） | 无 |
| 《缓冲》 | 无（BroadcastChannel） | 无 |
| 《对撞》 | 无 | 无 |

**结论：15 个方案都不需要新增权限。** 这是把隐私风险降到最低的关键设计。

# 21. 优先级与路线

## 21.1 推荐排序

| 序 | 方案 | 工作量 | 为什么这个顺序 |
| :--: | :--- | ---: | :--- |
| **1** | **和弦** | 1 天 | 技术假设最简单，**验证整个方向是否成立** |
| **2** | **缓冲** | 2-3 天 | 概念独特、零权限、零架构改动、回报最高 |
| 3 | 元素 | 4-5 天 | 概念最直观（"网页变关卡"），隐私最干净 |
| 4 | 折叠 | 2-3 天 | 独一份度最高之一，实现简单 |
| 5 | 沉睡 | 2 天 | 最巧的设计，但需先做节流探测 |
| 6 | 差分 | 4 天 | 社交属性好，但归一化是坑 |
| 7 | 断章 | 2-3 天 | 概念好，引导设计是关键 |
| 8 | 织网 | 3-4 天 | 最优雅，但需 L3 权限 |
| 9 | 回声 | 2-8 天 | 玩法最硬，声音降级是主要成本 |
| 10 | 对撞 | 5-6 天 | 对抗最强，但**联机信令是未解决阻塞项** |
| 11 | 倒带 | 3-4 天 | 独一份度最高，但接管后退风险大 |
| 12 | 纯滚 | 3-5 天 | 概念最好但**手感风险最高** |
| 13 | 对折 | 5-6 天 | 需改 surface 架构，建议延后 |
| — | 窄门 | 1-2 天 | **建议作为现有游戏模式，不做独立项目** |
| — | 像素考古 | 4k | **建议作为《元素》的纵向模式** |

## 21.2 三阶段路线

### 阶段 0：方向验证（1 天）

**只做《和弦》。**

- 技术假设：能否用物理修饰键状态做出有���味的玩法
- 验证目标：自己玩 10 分钟后是否想再玩一局

**如果《和弦》不成立，止损成本只有 1 天。**

### 阶段 1：核心可行性（2 周）

做《缓冲》+《元素》。

- 先建 DOM 采集层（20.1 方案），两项目共用
- 《缓冲》验证"浏览器行为型"玩法
- 《元素》验证"页面场地型"玩法
- **两条线并行，确认哪条更优**

### 阶段 2：深化（视阶段 1 结果）

- 若场地型更优 → 做《差分》《织网》
- 若行为型更优 → 做《折叠》《沉睡》《断章》
- 《倒带》《纯滚》建议等有真实用户反馈后再投入

## 21.3 关键决策点

| 决策 | 时机 | 重要性 |
| :--- | :--- | :--- |
| 《和弦》手感和可玩性 | 阶段 0 结束 | **最高：决定整个方向是否继续** |
| 场地型 vs 行为型哪个更优 | 阶段 1 结束 | 高：决定后续资源投入方向 |
| 联机信令方案 | 做《对撞》之前 | 高：无服务器约束下的联机是个真实难题 |
| 是否独立成第二插件 | 阶段 1 之后 | 中：若与主体定位冲突则拆出去 |

# 22. 风险清单

## 22.1 项目级风险

| 风险 | 影响 | 概率 | 缓解 |
| :--- | :--- | :--: | :--- |
| 用户不接受"改变浏览习惯" | 高 | 中 | 阶段 0 先验证 |
| 被误认为"浏览行为追踪器" | **极高** | 中 | 隐私分级 + UI 明示 + 只取几何不取内容 |

| 商店审核因"读页面内容"被拒 | 中 | 低 | 15 个方案零新增权限，隐私压力小 |

## 22.2 技术风险

| 风险 | 影响 | 缓解 |
| :--- | :--- | :--- |
| Shadow DOM 采集不到 | 中 | 实测 github 有 373 个 shadow host，需声明"简化关卡" |
| 结构贫瘠页不可玩 | **高** | 实测 zhihu 0 个标题、taobao h1+h2 仅 2 个。必须做**拒绝启动**机制 |
| 图片密集页过密 | 中 | 实测 CSDN 227 张图，需密度上限 |
| 后台节流影响心跳/逻辑 | 中 | 节流感知 + 降级设计 |
| 跨浏览器行为差异 | 中 | 各项目必须做 Chrome / Edge / Firefox 实测 |

## 22.3 合规与伦理

| 项 | 要求 |
| :--- | :--- |
| 隐私政策 | 必须单独说明"读取什么、不读取什么" |
| 权限 | 15 个方案零新增权限，是重要卖点 |
| 用户数据 | 提供"查看本地数据""导出存档""清除全部数据" |
| 可访问性 | 键盘操作、减少动效选项、不依赖声音 |
| 无诱导 | 不得用游戏奖励诱导点击或延长使用时间 |
